The Semantic Layer as a Tool Compiler

It produced the optimal toolset for an agent automatically, from the domain know-how the API schema never states.

A testbed study on the Chess.com API. Model: Claude Haiku 4.5. Benchmark of 28 cases. 2026-08-03.

Executive summary. I gave an agent a job, scouting a chess opponent, and instead of hand building its tools I let a second agent compile them from a semantic layer, a compact description of the domain. The compiled toolset, two tools, matched the three I had built by hand: the same quality across 28 cases, the same low cost, and the same set of APIs consulted, with no manual work and valid on the first attempt. The reason it works is the part that is easy to miss. The semantic layer carries the implicit know-how of the domain, the things that are true about chess data but appear nowhere in the API's data structures: that a result code like "timeout" means a loss on time, that ratings live under per time class keys, or what a useful scouting dossier even contains. That know-how is what lets the tools be built well, whether by a person or by the compiler. The study also settles two smaller questions. Enrichment inside the tools is what protects quality, since a raw approach collapses, and the generalized surface costs about 2.1 times more than a consolidated one. And handing the semantic layer to the agent as a run time skill is a net loss, between 5% and 28% more tokens, once the tools already carry it. This is an early result, one agent and one domain, so read it as a strong signal rather than proof; the appendices and the repository have the detail.

1. Context: objective, hypotheses and testbed

Background: the too many tools problem

It helps to start from what the field already knows, because it frames why this study matters. A growing body of evidence shows that an agent's ability to pick the right tool degrades as the number of available tools grows. Around 50 tools, frontier models still choose correctly 84 to 95 percent of the time. At 200 tools that falls to roughly 41 to 83 percent, and at around 740 tools it collapses to between 0 and 20 percent [1][2]. The Berkeley Function Calling Leaderboard measured accuracy dropping from 43 percent to 2 percent when the tool count grew from 4 to 51 across domains [2], and production teams commonly report a noticeable drop once more than 15 to 20 tools are in active rotation [3]. The usual failure modes are tool hallucination, where the model invents a tool name or fills arguments from another tool's schema, and positional bias, where tools in the middle of a long list are chosen less often [1][2].

Importantly, the mitigations the field recommends all point the same way, which is to keep the active surface small and well scoped: dynamic tool filtering, semantic routing, tool retrieval (often called Tool RAG), and consolidation [2][3][4]. This is the precedent for our work. The problem is real, so the useful question is not whether to limit the surface but how to do it well, and what role a semantic layer plays. That is what the rest of this report measures, and our results line up with this precedent: the tool count is a genuine lever, and a semantic layer is what lets you keep the surface small without losing coverage.

Objective

This is not a Chess.com product. It is a testbed built to measure, rather than assume, how the design of MCP tools and the role of a semantic layer affect a real LLM agent. We look at five things: cost, token usage, response time, the number of APIs consulted, and redundancy.

Hypotheses

  • H1. The size of the tool surface is a token tax paid on every turn, so shrinking it lowers cost without losing quality.
  • H2. The value of a semantic layer lies in data enrichment (normalization and aggregation), not in how tools are named or grouped.
  • H3. Injecting the semantic layer into the agent as a run time skill, when the tools are already enriched, does not pay for its cost.
  • H4. The semantic layer can act as a compiler that synthesizes the optimal per agent toolset automatically (the JIT approach).

Why Chess.com

The Chess.com Published Data API is a clean substrate for the experiment. It is public, read only and needs no authentication, so an autonomous agent runs with no credentials and no side effects. It offers objective ground truth, since ratings, results and openings are verifiable facts. It is serial and rate limited, which forces realistic connectivity engineering. It has no server side filtering, so aggregation becomes a genuine design problem, which is exactly the question a semantic layer answers. And its surface is rich but bounded, at 28 endpoints, small enough to reason about in full.

2. Proposed agents and the prioritized agent

Several analytic agents can be built on this API: an Opponent Scout for match preparation, a Leak Detector for performance leaks, an Opening Doctor for repertoire, a Progress Reporter for rating evolution, Club and Tournament analytics, and a Daily Digest, among others.

We prioritized the Opponent Scout for three reasons. First, it has to combine many endpoints (profile, ratings, monthly games, head to head), so it exercises aggregation, which is the core of the semantic layer. Second, it produces an objective and verifiable deliverable, a preparation dossier. Third, it spans both rich cases and edge cases, such as inactive or missing accounts and empty head to head records.

3. How the semantic layer integrates with MCP

The semantic layer can play three roles, and the study separates them on purpose.

RoleWhere it actsEffect
(a) Baked into the toolsInside each tool, as normalizers and aggregatorsThe agent receives clean, compact, decision ready data. This is what governs quality.
(b) Injected into the agentIn the agent's system prompt at run timeThe agent is handed the domain knowledge as text, resent on every turn. It does not change the tools.
(c) As a tool compilerAt build time, an agent reads the layer and writes the toolsetIt produces a specific, enriched toolset per agent, automatically.

The semantic layer in two forms: a skill and an information repository

The same semantic layer is materialized in two artifacts, aimed at two different readers.

  • As a skill (.claude/skills/chesscom-semantic-layer): packaged, portable domain knowledge, meaning the endpoint catalog, the normalized vocabulary, the glossary and the golden rules such as "aggregate, do not dump". It is written for a reasoning model to read. A skill can be handed to the agent at run time (role b) or to the synthesizer at build time (role c).
  • As an information repository (docs/SEMANTIC_LAYER.md, the machine readable tools_manifest.yaml and the primitives catalog): the canonical, structured source of truth from which enriched tools are generated. It is written for a code factory to consume. This is what powers role (a) and feeds the factory used in role (c).

A real excerpt of each makes the distinction concrete. First the skill, written for a model to read, which states the vocabulary and the rules in prose:

### Normalized vocabulary (the domain language)
- Time class: bullet | blitz | rapid | daily   (from time_class)
- Outcome:   map raw result codes -> win | loss | draw, plus a reason
             (checkmate, resignation, timeout, agreement, stalemate, ...)
- Opening:   parse the eco URL into { eco_code, name }
- Timestamps: convert epoch -> ISO-8601 UTC before presenting

### Golden rules
- Aggregate, don't dump. Never return hundreds of raw games; filter and summarize.
- Normalize before presenting. Raw epochs and result codes confuse users and models.

Then the repository, written for the factory to consume, which encodes the same ideas as a buildable specification:

# tools_manifest.yaml (excerpt) - the machine-readable source of truth
capabilities:
  ratings:
    source: { fetch: endpoint, path: player/{username}/stats }
    shape:  { aggregator: normalize_stats }      # enrich, do not return raw

consolidation:
  tools:
    - name: chess_scout_player
      description: One-call scouting bundle: identity, ratings, form, openings, activity.
      bundle: [ profile, ratings, performance, openings, activity ]   # 5 capabilities, 1 call

In short, the skill is the knowledge form and the repository is the specification form. They describe one domain model in two representations. The experiments below show that the repository form, which produces enrichment inside the tools, is where the value sits, while the skill form is useful for building the tools but a poor idea to hand to the agent at run time.

The real asset is implicit domain know-how. Look at what those excerpts encode: that a raw result code maps to win, loss or draw plus a reason, that ratings sit under per time class keys, that an opening comes from an ECO URL, that you aggregate rather than dump raw games. None of this is present in the JSON the API returns. It is knowledge about the domain, the kind a chess analyst carries in their head, the meaning behind the data structures rather than the structures themselves. That is exactly what a good toolset has to embody, and it is why the semantic layer matters: it captures that know-how once, so the tools inherit it, whether a person writes them or the synthesizer compiles them. This idea runs through the rest of the report.

What a consolidated tool is

The alternatives below differ mainly in one choice, so it is worth defining it. A tool can map to a single API endpoint, or it can consolidate several into one call.

A single endpoint tool does one thing. For example chess_get_player_stats simply returns the stats endpoint:

# A tool that maps to a single API endpoint
chess_get_player_stats(username)
  -> GET player/{username}/stats
  -> returns that one endpoint's data. To build a dossier the agent must also call
     chess_get_player_profile, chess_list_archive_months, chess_get_month_games ...
     and then compute ratings, form and openings itself, across several turns.

A consolidated tool bundles several endpoints and does the aggregation for the agent, returning a result that is ready to use:

# A consolidated tool that bundles many endpoints into one call
chess_scout_player(username, months)
  -> fetches profile + stats + several months of games internally
  -> returns a ready dossier substrate: identity, ratings, form (win/draw/loss by
     class and colour, streaks), opening highlights and activity. One call, done.

E1 is built entirely from single endpoint tools, so the agent stitches the dossier together itself. E3 and E4 are built from consolidated tools. The enrichment that a consolidated tool performs is exactly role (a) of the semantic layer. Consolidated tools carry several concrete advantages over single endpoint ones:

  • Fewer turns. One call returns the dossier substrate, instead of a chain of calls the agent has to sequence and combine.
  • Fewer definition tokens per turn. A small surface is what gets resent on every turn, so the per turn tax is lower.
  • Less selection ambiguity. With a few well scoped tools there is little room to pick the wrong one, which is the exact failure mode that grows with tool count in the background above.
  • Same coverage. A consolidated tool consults the same endpoints, it just bundles them, so nothing is lost.
  • Enrichment done once. Normalization and aggregation happen server side and arrive ready to use, rather than being left to the agent across turns.

Alternatives evaluated

Each alternative materializes the tools differently. All of them share the same connectivity layer and the same tool agnostic agent. The design has two axes: whether the returned data is enriched, and how large the tool surface is.

E1. Granular and generalized (the full toolset, 31 tools)

Thirty one small tools, roughly one per endpoint, each enriched. The agent composes several calls to build a dossier. It gives full, reusable coverage, but the large surface is resent on every turn and the agent takes many turns, which raises token cost and encourages it to call more tools than needed.

E2. Generalized plus consolidated (the full_completa toolset, 42 tools)

The 31 granular tools plus 11 consolidated ones, deliberately overlapping. We built it to study the confusion a redundant surface causes. The agent tends to mix granular and consolidated tools, so cost stays high even though the consolidated tools cut the number of turns.

E3. Curated and consolidated (the vtoolsconsolidadadinamica toolset, 3 tools)

Three consolidated tools generated from the machine readable manifest, each bundling several capabilities into one call. This is the best result a person can design: minimal surface with full enrichment. Its limitation is that it has to be curated by hand for every new agent, so it does not scale on its own.

E4. Compiled by the semantic layer, the JIT approach (the dinamico_jit_sintetizada toolset, 2 tools)

A Claude Code agent, the tool synthesizer, reads the semantic layer, a closed catalog of primitives, and the agent's mission, and writes a validated tool spec that the factory materializes. Synthesis happens once per agent at build time and is cached, then the object agent runs against the resulting tools. It automates the curation that E3 does by hand. Its one weakness is that the current factory refetches the same monthly archives once per bundled capability, which raises latency, a point addressed in Appendix B. Full detail is in Appendix B.

Option B is discarded as unviable. This approach returned raw API data with no normalization or aggregation. In a bounded nine case probe it collapsed: raw payloads averaged about 166,000 tokens per case, one matchup reached about 650,000, and context overflowed in four of the nine cases, leaving a usable dossier in only five. It is not treated as a candidate. It is kept as evidence that data enrichment is mandatory, not optional.

5.3 The effect of injecting the skill into the agent

On all three enriched surfaces, handing the skill to the agent at run time raises cost, because its text, about 1,400 tokens, is resent on every turn and outweighs the small discipline it adds, with no gain in quality (28 of 28 either way): E1 goes from 29,914 to 34,591 tokens (plus 16%), E2 from 28,252 to 29,639 (plus 5%), E3 from 11,470 to 14,668 (plus 28%). The conclusion is clear: the semantic layer is valuable when it builds the tools, but not when it is handed to the agent as run time text, since the tools already carry it.

5.4 Conclusions

  • Enrichment governs quality. Every enriched variant delivers 28 of 28. The un enriched Option B collapses. This is not negotiable.
  • Surface size governs cost. The consolidated approaches, E3 and E4, cost about $17 per 1,000 dossiers, against $36 to $33 for the generalized ones, which is roughly 2.1 times cheaper, at the same quality.
  • E3 and E4 are tied on cost, on tokens and on distinct APIs, where E4 is in fact the leanest at 6.6 endpoints per case. They consult the same endpoints and produce equivalent dossiers. E4 packs eleven capabilities into two tools, a superset of E3, so it reads no less information.
  • The skill handed to the agent never pays. It is a net loss on all three surfaces.
  • The binding constraint is scope, not the raw tool count. Every enriched variant delivered full quality, including the one with 42 tools, because the tools were well scoped and the task was clear. What raised cost was the larger surface, and what caused the extra turns in E2 was redundancy, not the count itself. This matches the background: within a well designed system the count is mainly a cost lever, while at much larger scales, in the hundreds, selection accuracy collapses [1][2]. The right lever is therefore to keep the active surface small and well defined. Consolidation and the semantic layer do exactly that, which places our recommendation in line with the mitigations the field already recommends [2][3][4], such as tool retrieval and semantic routing. In our case the semantic layer goes one step further, since it also builds the enriched tools and, through the JIT approach, composes the minimal surface automatically.
  • The asset is the domain know-how, not the tool code. Whether a person writes the tools or the compiler builds them, what makes them good is the implicit domain knowledge in the semantic layer, the meaning behind the API's data structures. Capture it once and you can build, or compile on demand, the right tools for any agent in that domain.
Recommendation. Build the semantic layer into the tools, keep the surface small, and do not hand the layer to the agent as a run time skill. For a single, fixed agent where the cost of curation does not matter, the hand curated E3 is a perfectly good choice. The strategic choice, and our recommendation, is E4, the JIT approach: it matches the hand curated optimum on cost, quality and the number of APIs consulted, and it reaches that result automatically, with no manual curation, scaling to many agents from one semantic layer. One engineering task closes the last gap, namely caching the archive fetch inside a bundle so the same data is not fetched twice, which lowers E4's latency and benefits every consolidated variant.

Two things stand out. First, they cover the same ground. Both consult the same endpoints and produce equivalent dossiers, which the benchmark confirmed. It knows because the semantic layer encodes the implicit know-how of the domain. That is the thread of this whole report: the asset is the know-how, not the tool code, and once it is captured, the right tools can be written by a person or compiled on demand.

Appendix A. Technical design of the test environment

The environment is built so the tool layer is the only thing that changes between runs. Everything else, the agent, the connectivity, the harness and the workload, is fixed and shared, which makes any difference in the results attributable to the tools alone.

The Opponent Scout is an agent, not a script

The Opponent Scout is a genuine autonomous agent, and it has three parts. First, a mission prompt in .claude/agents/opponent-scout.md, written to be tool agnostic, so the agent never assumes tool names and adapts to whatever the server exposes. Second, a model, Claude Haiku 4.5, which does the reasoning and decides what to do. Third, an agentic loop, the Anthropic tool runner, which lets the model choose a tool, call it over MCP, read the result, and repeat until it writes the dossier. Because tool selection is genuine rather than scripted, comparing toolsets measures real behaviour, which is the whole point of the benchmark. A deterministic version of the same playbook also exists, used offline to validate the harness without spending model calls.

How a benchmark run works

  1. Choose a variant with CHESS_MCP_TOOLSET, and for the JIT case a spec with CHESS_MCP_JIT_SPEC.
  2. For each of the 28 cases, the runner starts a fresh MCP server with tracing on and connects the agent with the case prompt.
  3. The model selects and calls tools on its own. Every call passes through the tool boundary, which records the name, arguments, latency, size and outcome.
  4. The agent's dossier and its token usage are captured, and the trace is turned into metrics.
  5. Runs are launched sequentially, since the API is serial, and each one produces a JSON dataset, an HTML report and per case traces, all reproducible.

How the metrics are collected

A small guard around every tool records the call to a JSONL trace, switched on by environment variables so normal use carries no overhead. Token usage comes from the model's own counters, summed over the turns of a case. The number of distinct endpoints consulted is recovered from the client's request logs. Since nothing in the agent changes from one variant to the next, every difference in the numbers can be attributed to the tool layer.

Appendix B. The JIT tool synthesizer

What it is

A Claude Code agent, defined in .claude/agents/tool-synthesizer.md, that acts as a tool compiler. Given an agent's mission, it reads the semantic layer, in its skill form, and a closed catalog of primitives, and writes a validated tool spec. It writes no Python, since it only composes existing primitives, and it does not run the object agent.

How it works

  1. Synthesis, at build time, once per agent and cached: it reads the skill, the primitives_catalog.yaml and the mission, and emits generated_jit_<agent>_spec.yaml.
  2. Validation and repair: the validate_spec gate checks the schema, that every primitive exists, that the factory can build the tools, and that a live smoke call returns data. The agent iterates until the gate passes.
  3. Materialization, at run time: the dinamico_jit_sintetizada variant reads the spec, through CHESS_MCP_JIT_SPEC, and the existing factory builds the MCP tools.

How it fits and what it adds

  • It is purely additive. The spec is the only contract between build and run, written in the schema the factory already reads, so no existing variant or harness changes.
  • It reached the curated result (E3) with no manual curation, and produced a valid spec on the first attempt, with no repair loop. This is early evidence that the semantic layer improves the generation itself.
  • For the Opponent Scout it produced two tools: chess_player_profile, which bundles nine capabilities, and chess_matchup, which bundles two. They consult the same endpoints as the curated set and produce equivalent dossiers.
  • One point to improve: the single large tool bundles seven capabilities based on game archives, and the factory currently fetches the same monthly archives once per capability. This raises HTTP volume and latency, although the agent still consults only 6.6 distinct endpoints. Caching the fetch inside a bundle removes it and helps every consolidated variant.
  • It scales. The real payoff is many agents, each getting a near optimal toolset from one semantic layer, at no extra curation cost.

On accounting, the synthesis itself cost about 59,000 tokens, once per agent and cached, not per request. On a single agent E4 ties E3 plus that one time cost, and its decisive advantage is removing the manual step and scaling.

Appendix D. A multi-agent example: the Matchup Strategist

To test whether one semantic layer can serve more than one agent, we built a small multi-agent system. Given an opponent's name, it recommends the style to play against them and the openings, as White and as Black, most likely to beat that player. It runs two specialists, each with its own toolset compiled by the JIT synthesizer from the same semantic layer, followed by a synthesis step that has no tools.

The agents and the tools the JIT compiled for each

Each specialist was given a short mission, and the synthesizer wrote its toolset from the semantic layer. The two toolsets are genuinely different, each scoped to what its mission needs.

The contrast is the point. The Scout's tools touch player/{opponent}, player/{opponent}/stats, player/{username}, player/{username}/games/(monthly archives), player/{username}/stats. The Opening Doctor's single tool touches only player/{username}/games/(monthly archives), because a repertoire is derived from games, not from the profile or the stats endpoint. The synthesizer scoped each agent to exactly the APIs its job requires, with no overlap beyond what the task shares. The Matchup Strategist itself uses no tools; it only reads the two briefs and writes the plan.

Results

10 of 10 players completed with no errors. Average per case: 23,761 total agent tokens (Opponent Scout 11,635 + Opening Doctor 7,639 + synthesis 4,487), and 2 tool calls, one per specialist, since each resolves its analysis in a single consolidated call. Each recommendation combined the two briefs into a concrete plan, for example steering a game toward an opponent's worst-scoring opening as identified by the Opening Doctor and justified by a weakness found by the Scout.

The JIT toolset versus a generalized one plus the skill

To check whether the tailored JIT toolsets were actually worth it, we ran the same ten players a second time, equipping the agents differently. Instead of a JIT-compiled toolset, each specialist was given the generalized full_completa_con_consolidadas toolset (42 tools) with the semantic-layer skill injected into its prompt at run time. This is the semantic layer used as a repository that built the tools plus a run-time skill, rather than as a compiler. Both runs produced a usable plan for all ten players, so the comparison is about cost, not quality.

The generalized toolset plus skill costs about 2.7 times the tokens of the JIT approach (23,761 against 63,444) and makes 8 tool calls against 2, for the same result. The whole difference sits in the two specialists: with 42 tools and the skill in the prompt they take more turns and carry a much larger surface on every turn. The synthesis step is nearly identical (4,487 against 4,566), as expected, since it uses no tools and no skill. Giving each agent a tailored, minimal toolset compiled from the semantic layer beats giving it the full surface with the skill as a run-time guide, which is the same conclusion the single-agent benchmark reached, now confirmed across a multi-agent system.

This closes the scale question the study left open. From one semantic layer, the synthesizer produced two distinct, minimal, valid toolsets for two different agents, each scoped to its own APIs, and the system combined them into a decision-ready plan at roughly a third of the cost of the generalized alternative. The domain know-how, captured once, was enough to equip a new agent with no extra work. That is the multi-agent case for the semantic layer as a tool compiler.
